# Pilot user, value mechanism and limits

The target user is a platform or knowledge engineer operating a cached support assistant for frequently revised policies/product configurations. The buyer hypothesis is the owner of that application's retrieval/generation bill and stale-answer incidents. Existing Ragas quality evaluation and dbt freshness workflows demonstrate that quality/freshness monitoring is an established job; they do not validate demand for this package.

A pilot connects an existing ingestion pipeline to the documented JSON protocol. On ingestion, record immutable source versions, TTL policy and normalized fact keys. On answer generation, declare claim dependencies and alternatives. At read time, use `evaluate` to gate reuse and preserve returned witnesses for diagnosis. On source changes, use `compare` to evict actual newly blocked answers, route conflict tasks for review, and run `plan` to limit evidence checks. Add corrected versions and regenerate/rebind claims only after validation. An immutable old file plus the new file gives a reproducible incident snapshot.

The executable synthetic contrast demonstrates two mechanisms: avoid discarding answers with still-valid alternatives; block disagreements that timestamps alone miss. For a deliberately hypothetical batch of 300 cached answers matching the fixture, and an assumed regeneration cost of $0.01 each, avoiding 200 unnecessary regenerations versus the whole-corpus gate would avoid $2 in that batch before integration/review overhead. Neither the workload mix nor unit cost is measured. Against the flat gate, 100 unnecessary regenerations are avoided, while 100 known conflicting answers are withheld; withholding can increase latency/manual work, so it is not automatically a financial saving.

Pilot measurements should include: extraction/normalization effort, proportion of answers with meaningful alternatives, reviewer-confirmed stale/conflict incidents, reruns avoided, total model/ingestion/review cost, request latency, and false conflict rate. A pilot fails if adapter maintenance or conflict review exceeds avoided cost/risk. It also fails if important disagreements cannot be represented by scoped scalar facts.

Potential paid work is integration/support for source adapters and policy normalization, not an implemented hosted product. Current support boundary is the local protocol and deterministic decision engine; no SLA, authentication service, vector database or managed connector is included. Actual customers, adoption, revenue and willingness to pay are unknown. MIT licensing permits commercial use; users can inspect or replace the engine without a hosted dependency.
